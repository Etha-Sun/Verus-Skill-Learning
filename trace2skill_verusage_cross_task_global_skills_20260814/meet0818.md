# 08/18 组会汇报：跨任务全局 Verus Skill 学习

## 一句话结论

在同一组 20 道验证题上，no-skill 通过 16 题，M_core 通过 14 题，native-compressed 候选通过 13 题并被拒绝，semantic-reduce 最终通过 17 题。Semantic 分支正式接受 Candidate 1 和 Candidate 4；Candidate 8 和 Candidate 11 也达到 17/20，说明内容具有行为信号，但分别因为 token 开销和缺少显著效率收益而未晋级。

> 当前结果均为验证集上的单次运行，用于选 skill 和分析机制；还不能当作最终泛化结论。Sealed test 尚未运行。

## 1. Semantic-reduce 如何从 MAP/REDUCE 生成 Candidate

### 简明版

可以把整个过程理解成“先记便签，再分类装订，最后逐本试用”：

1. **MAP：从轨迹中提炼便签。** 输入是 40 条训练任务记录中的 160 个 memory item（87 条成功经验、40 条失败原因、33 条失败经验），并提供冻结的 M_core 作为编辑基线。40 条记录分成 8 个 batch，每批 5 条；MAP 独立提炼出 19 个原子 skill 修改建议。此时只产生候选建议，不直接修改最终 skill。
2. **Semantic routing：按证明机制分类。** 将 19 个 MAP item 按语义分入 12 个机制 family，例如 proof grounding、temporal prerequisites、equality/trigger、serialization 等。每个 MAP item 恰好进入一个 family，保证不遗漏、不重复。
3. **Within-family REDUCE：同类建议去重合并。** 只在同一 family 内用 Trace2Skill 原生 REDUCE 合并重复或互补建议；不做跨 family 的全局压缩。最终每个 family 形成一个 patch bundle，因此得到 12 个顺序 Candidate。
4. **Candidate construction：落到真实 skill 文件。** 每个 bundle 相对“当前已接受的 incumbent skill”翻译为对 `SKILL.md` 和 `references/*.md` 的具体编辑，形成不可变 skill snapshot。
5. **Held-out gate：逐个在同一验证集试用。** 每个 Candidate 在同一 20 道验证题上运行；只有成功率提升且资源增长在上限内，或成功率持平但有显著效率提升时，才替换 incumbent。被拒绝后，下一个 Candidate 仍从上一个已接受版本构造。

### 与 native-compressed 的区别

两条分支共享同一份 MAP 输出（19 个 item）。Native-compressed 把全部 item 做一次全局 REDUCE，只产生 1 个大 Candidate、做 1 次 gate；semantic-reduce 先按语义拆成 12 个 family，再分别 REDUCE 和 gate。后者的优势是可以保留局部有效的知识，而不必让一个坏修改拖累整个大 patch。

### 12 个 Candidate 的语义对应

| Candidate | Semantic family | 核心语义 |
|---|---|---|
| 1 | `proof-grounding` | 证明落地：注释不算证明；把定义展开成显式事实，并用 `assert`、`reveal`、已有 lemma 或量词实例化补齐真实证明。 |
| 2 | `exact-target-verification` | 精确目标验证：修改和最终验证必须落在题目指定文件；临时副本只能用于调试，证明改动必须回填原目标。 |
| 3 | `trust-boundary-shortcuts` | 信任边界与捷径约束：禁止新引入 `assume`、`admit`、伪 `external_body`、空洞的外延性公理等绕过证明的手段。 |
| 4 | `temporal-action-prerequisites` | 时序/动作引理的前置条件：先证明状态级条件、稳定性、动作建立或 enabledness，再应用时序规则，而不是删掉失败的 lemma。 |
| 5 | `in-place-proof-edits` | 原地 proof-only 修改：保留宏、可执行代码、规格和签名，只在指定文件中补证明，不以旁路副本作为交付结果。 |
| 6 | `definitional-inspection` | 定义检查与递归对齐：先看真实定义和递归方程，再匹配归纳变量、`decreases` 与展开方式，避免凭名字猜 lemma。 |
| 7 | `temporal-proof-patterns` | 通用 TLA/时序证明模式：稳定性、trigger、存在量词桥接、`leads_to` 分解与传递、suffix induction、`TempPred` 等式和 entailment 组合。 |
| 8 | `proven-mechanism-patterns` | 已验证机制配方：汇总能直接复用的具体解法，如时序互蕴证等式、有限集合归纳、宏环境恢复、精确 ghost witness 和空容器证明链。 |
| 9 | `verus-proof-patterns` | 可复用 Verus 证明模式：高阶 spec lambda/entailment、集合与 map 成员关系、时序稳定性组合、有限集合或 map 归纳及 proof-only 工作流。 |
| 10 | `equality-trigger-patterns` | 等式与 trigger：用 `=~=` 处理外延等式，用 `#[trigger]` 驱动逐点实例化，并覆盖 suffix 组合、递归时序证明和时序谓词等式。 |
| 11 | `recurring-verus-patterns` | 高频 Verus 模式：`leads_to` 传递链、用 `init_invariant` 建立 `always(lift_state(P))`、大合取稳定性、多重集空性和 `always` 的逐点使用。 |
| 12 | `serialization-proof-patterns` | 序列化与 marshalability：必要时手工展开宏，维护含 `old(argument)` 的循环不变量，处理空序列、字节长度、前后缀单射和可序列化前置条件。 |

## 2. 验证集结果

所有组使用相同的 20 道验证题，actor 为 DeepSeek V4 Pro，单题 Codex actor 上限 900 秒；成功必须同时通过最终 Verus 和 Lynette 检查。

| 实验组 | 原始候选结果 | Gate 后最终结果 | 通过率 | 说明 |
|---|---:|---:|---:|---|
| No-skill | 16/20 | 16/20 | 80% | 不加载 skill |
| M_core only | 14/20 | 14/20 | 70% | 两条候选分支的共同起点 |
| M_core + native-compressed-gated | 13/20 | 14/20 | 70% | 唯一 native Candidate 退化，被拒绝；最终退回 M_core |
| M_core + semantic-reduce-gated | 最佳 Candidate 17/20 | 17/20 | 85% | Candidate 1、4 被接受；最终保留 Candidate 4 |

最终版本 skill 在这 20 题上的推理总费用为 USD 0.8223、总 wall time 为 6272.94 秒；平均每题约 USD 0.0411、313.65 秒（约 5 分 14 秒，包含 3 道超时题）。

主要观察：

- Semantic 最终版本比 M_core 多通过 3 题（14 → 17），比 no-skill 多通过 1 题（16 → 17）。
- M_core 本身低于 no-skill，说明“加入通用 skill”并不自动带来收益；真正的增益来自后续经过 held-out gate 筛选的局部语义知识。
- Native 大 patch 从 14 降到 13，因此被 gate 正确挡回；semantic 的细粒度 Candidate 则允许只接受有效 family。

## 3. 有效 Candidate 案例分析

这里区分两类“有效”：Candidate 1、4 是 gate 正式接受的有效更新；Candidate 8、11 达到 17/20，内容对模型行为有明显影响，但没有满足效率 gate，因此只能称为“行为上有信号”，不能算最终 skill 的组成部分。

### Candidate 1：Proof grounding（正式接受）

- **语义主题：** 把自然语言推理落成 Verus 可检查的 proof term。
- **核心内容：** 明确禁止把注释当证明；要求使用 `assert`、`reveal`、lemma call、量词实例化等真实 proof step；对 `entails`、`always`、`satisfied_by` 等 temporal/higher-order 定义先展开为显式量词事实。
- **效果：** M_core 14/20 → Candidate 1 16/20，新增解出 2 题，且没有丢题：
  - `IR__marshal_v__impl0__deserialize`
  - `AL__unpack_conditions_from_spec`
- **资源表现：** 总 token 比 M_core 下降约 1.7%，primary uncached token 下降约 13.2%，因此是较干净的正收益。
- **解释：** 它补的是“模型知道道理但没有写出 verifier 可消费的证明步骤”这一通用缺口。

### Candidate 4：Temporal/action prerequisites（正式接受，最终版本）

- **语义主题：** temporal/action lemma 的前置条件与证明顺序。
- **核心内容：** lemma 调用失败时保留调用并补齐 precondition；调用 `wf1`、`leads_to_stable` 等规则前，分别证明 stability、action establishment、enabledness 等状态级条件；先证明 state-level implication，再提升到 `always`/`entails`。
- **效果：** Candidate 1 16/20 → Candidate 4 17/20，新增解出验证题 3，且没有丢题。
- **资源表现：** 相对 Candidate 1，总 token 增加约 5.2%，但总 wall time 下降约 3.7%；成功率提升使其通过 gate。
- **解释：** 它避免模型直接套 temporal 大定理而跳过隐藏前提，对 Anvil controller liveness 证明尤其有帮助。

### Candidate 8：Proven mechanism patterns（行为上有信号，未接受）

- **语义主题：** 一组来自成功轨迹的具体“证明招式表”。
- **核心内容：** temporal predicate equality 的双向 entailment、嵌套 temporal operator 展开、有限集合递归归纳、macro/environment 恢复、精确 ghost witness、空容器 pipeline。
- **效果：** 与 Candidate 4 相同，仍为 17/20；成功题集合也完全相同。超时从 3 题降到 2 题，但第 16 题变成及时提交后 Verus 失败，因此没有获得第 18 个成功。
- **效率变化：** 总 wall time 下降约 10.9%，但总 token 增加约 21.2%，超过同成功率 Candidate 的 10% 局部资源上限，也超过相对 M_core 的 1.2 倍 token 上限，因此被拒绝。
- **原因分析：** 主 skill 中的路由条件太宽，20 题中有 18 题实际读取了新 reference；reference 进入上下文后在后续请求中反复携带，token 增长主要来自 cache-hit input。说明“具体招式表”可能有用，但需要更精确的按题型路由。

### Candidate 11：Recurring Verus patterns（行为上有信号，未接受）

- **语义主题：** 高频 temporal、state-machine 和 multiset 证明模板。
- **核心内容：** `leads_to` transitivity 的 lemma chain、`always(lift_state(P))` 的 `init_invariant` 模板、大型 `always` conjunction 的稳定性组合、multiset length-zero 双向证明、从 `always(P).satisfied_by(ex)` 得到 pointwise goal。
- **效果：** 仍为 17/20，但发生一次题目交换：新解出历史上很难的第 15 题，同时丢掉 Candidate 4 已解出的第 19 题。
- **效率变化：** 总 token 与 Candidate 4 基本持平（约 -0.13%），但 primary uncached token 增加约 13.3%，wall time 增加约 5.3%；综合效率没有达到预设阈值，因此被拒绝。
- **解释：** 这类模板确实能改变证明策略并突破特定难题，但适用面和副作用还不稳定，适合进一步拆分成更窄的按需 reference。

## 4. 最难的验证题：3、11、15、16

这四题在本轮多数组合中反复超时或失败，但它们并非全部是原始 Claude 未通过题。

| 题号 | 任务（缩写） | 原始 Claude 状态 | Claude 用时 | 本轮观察 |
|---:|---|---|---:|---|
| 3 | AC `api_request_other_than_pending...maintains_matching_pods` | **FAILED** | 951.04 s | no-skill、M_core、Candidate 1 超时；native raw、Candidate 4/8/11 解出。Candidate 4 的 temporal prerequisite 指导在这里带来净增益。 |
| 11 | AC `from_after_send_delete_pod_req_to_receive_ok_resp` | **FAILED** | 1459.75 s | no-skill、M_core、native 以及 Candidate 1/4/8/11 全部超时，是最稳定的共同失败点。 |
| 15 | IR `delegation_map_v::set` | **FAILED** | 973.35 s | no-skill、M_core、native、Candidate 4/8 超时；Candidate 11 首次解出，但同时在另一题发生退化。 |
| 16 | IR `lemma_seqno_in_un_acked_list` | **VERIFIED** | 57.50 s | 原始 Claude 很快通过，但本轮 DeepSeek 各主要组均未通过；Candidate 8 从超时变为 604 秒内提交，但最终 Verus 失败。 |

结论：

- 第 3、11、15 题确实是历史 Claude 失败题；第 16 题不是，Claude 当时 57.5 秒即验证通过。
- “难题”具有明显的模型与 harness 条件依赖性。第 16 题说明历史 Claude 标签不能完全预测 DeepSeek V4 Pro + Codex CLI 设置下的难度。
- 第 11 题是当前最明确的后续 case study：所有主要条件都失败，可用于分析共同缺失的证明机制。
- 第 3 和第 15 题适合做正向 case study：它们分别被 Candidate 4 和 Candidate 11 的语义知识突破，可以对比具体 proof trajectory，研究 skill 如何改变策略。
