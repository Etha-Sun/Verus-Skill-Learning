# Experiment Plan

**问题**：VeruSAGE hands-on trace 里有丰富的 proof-repair 轨迹，但我们还没有一个可执行、可审计的 metric 来判断某个 skill/rationale 是否真的给当前 repair state 增加了有用信息。

**方法主张**：把 candidate artifact 当作 trajectory-conditioned context，用三类 target 上的 log-likelihood difference 衡量 information gain：下一步 action、完整 final proof、以及局部 proof patch span。

**日期**：2026-07-04

## Claim Map

| Claim | 为什么重要 | 最小可信证据 | 对应实验块 |
|---|---|---|---|
| C1: trajectory-conditioned artifact 有可测量的 proof-repair information gain | 这是 self-evolving skill/rationale 可以在 live rerun 前被评估的核心依据 | trace-derived artifact 在 `log P(target | state, artifact) - log P(target | state)` 上稳定高于 generic/irrelevant control | B1, B2, B3, B4 |
| C2: local IG metric 比 naive full-proof IG 更可靠 | full proof 很长、非唯一、噪声大，reviewer 会质疑 metric 是否有意义 | action IG 和 patch-span IG 比 full-proof IG 更能区分 artifact；full-proof IG 作为并列 metric 保留但标注风险 | B2, B3, B4 |

需要排除的反主张：

- 信息增益只是长 proof tokenization / formatting artifact。
- artifact 生成时偷看了 final proof。
- patch span 是人工挑选、不可复现的。
- action IG 只是同数据集记忆，没有 split 控制。

## Paper Storyline

主文需要证明：

- hands-on VeruSAGE traces 可以被切成稳定 repair states，并构造 action/full-proof/patch-span 三类 target。
- information gain 不只是漂亮公式，而是能反映局部 proof-repair decision 的有用 metric。
- 系统会保存 token-level 概率和 logprob，保证每个 aggregate score 可追溯。

附录可以支持：

- scorer sensitivity：本地 QwQ-32B vs DeepSeek/OpenAI/Gemini cloud logprobs。
- motif/TLA artifact 作为后续扩展。
- 更多 prefix schedule，而不只 `early/middle/late`。

第一版明确不做：

- live rerun skill injection；
- RL reward training；
- motif/TLA 作为 must-run；
- hands-off trace slicing。

## 核心定义

### Trace Scope

第一版只用 hands-on verified traces。

理由：

- hands-on trace 的 state/action 边界更清楚；
- 第一阶段目标是验证 metric，不是证明完整系统提升；
- hands-off 仍然是 scalability 目标，但等 metric 成立后再做。

### Stable Prefix State

不要在任意 token 位置截断。`state_t` 只在 VeruSAGE repair loop 的稳定边界截断：

```text
verifier feedback 已经产生之后
下一次 agent repair attempt 开始之前
```

每个 `state_t` 尽量包含：

- 当前 code；
- 当前 verifier result 和 error list；
- selected error；
- attempt index；
- 历史 error/action/candidate outcome；
- 上一次 patch/candidate metadata；
- project/task/model id；
- 不能包含 final proof text。

这和 VeruSAGE 的真实 loop 对齐：

```text
verus_eval -> select one error -> agent repair -> observe/reason/act -> validate -> next verus_eval
```

ORA phase 对解释有用，但实验截断点不是任意 `observe/reason/act` 内部，而是 verifier-feedback 后的下一次决策点。

### Prefix Schedule

每条 verified trace 最多取三个 prefix：

- `early`：initial verifier feedback 后的第一个 repair state；
- `middle`：中位 repair state；
- `late`：最终成功前最后一个 failed state。

如果 trace 可用 states 少于 3 个，就保留全部，并记录 `prefix_count`。

### Candidate Artifacts

Must-run artifact：

- `none`：baseline，无 artifact；
- `generic_skill`：通用 proof-repair guidance，不针对当前 trace；
- `trace_rationale`：只基于 `state_t` 生成的 rationale / counterexample-like explanation；
- `irrelevant_control`：看起来合理但和当前 task 无关的 control。

Nice-to-have：

- `motif_skill`：quantifier/arithmetic/TLA-style skill，第一版不作为 must-run。

硬性 leakage rule：

```text
artifact generation 不能看到 final proof；
final proof 只能作为 scorer 的 target。
```

## Experiment Blocks

### B1: Data Slicing and Target Construction

- 检验 claim：C1 的前置条件。
- 为什么需要：只有 `state_t`、action target、full proof target、patch span target 都是确定和可审计的，后面的 IG 才有意义。
- 数据 / split / task：
  - 20-50 条 hands-on verified traces；
  - 只用 train/dev；
  - held-out traces 留给后续验证。
- 比较系统：
  - 无模型比较；这个 block 验证 extraction。
- 指标：
  - parsed verified traces 数量；
  - usable prefix states 数量；
  - `primary_action` 覆盖率；
  - final proof target 覆盖率；
  - non-empty patch span 覆盖率；
  - action/full-proof/patch-span target length distribution。
- 设置：
  - 建 manifest：每行一个 `(trace_id, prefix_id, target_type)`；
  - raw trace 路径只做 read-only reference；
  - derived manifest 写到 `verus-self-evolve-scaffold/runs/` 或 `research_memory/`。
- 成功标准：
  - 至少 80% sampled verified traces 能得到 action 和 full-proof target；
  - 至少 60% 能得到 reviewer-auditable patch span。
- 失败解释：
  - 如果 action metadata 缺失，action IG 降级到 coarse action category 或 peer-success prior；
  - 如果 patch span 经常为空或过大，需要改 code-region extraction。
- 表格目标：
  - appendix data construction table。
- 优先级：MUST-RUN。

### B2: Action Information Gain

- 检验 claim：C1, C2。
- 为什么需要：action IG 最贴近“改善 repair decision”这个目标。
- 数据 / split / task：
  - 使用 B1 的 prefix manifest。
- 比较系统：
  - baseline context：`state_t`；
  - `state_t + generic_skill`；
  - `state_t + trace_rationale`；
  - `state_t + irrelevant_control`。
- Target definitions：
  - 主 target：成功 trajectory 中记录的 VeruSAGE `primary_action`；
  - 次 target：由 `primary_action` 派生出的 coarse action category；
  - 次 target：同一 state/error signature 下 train split 中成功率最高的 action。
- Metrics：
  - `IG_sum = sum_logprob(target | state, artifact) - sum_logprob(target | state)`；
  - `IG_avg = avg_logprob(target | state, artifact) - avg_logprob(target | state)`；
  - positive/zero/negative IG rate by artifact type；
  - rank accuracy：`trace_rationale` 是否排在 `irrelevant_control` 前；
  - successful-trajectory action target 和 peer-success action target 的 agreement。
- 设置：
  - 第一实现只做 `primary_action`；
  - peer-success target 的 state/error signature 只能从 train split 统计；
  - action label 序列化为 canonical string。
- 成功标准：
  - `trace_rationale` 的 mean/median IG 高于 `irrelevant_control`；
  - 结果在 primary action 或 coarse action 上至少一个稳定成立。
- 失败解释：
  - action IG flat：artifact 可能没有影响局部 action probability；
  - irrelevant control 高分：prompt formatting 或 scorer bias 主导。
- 表格目标：
  - 主文 Table 1：Action IG by artifact type。
- 优先级：MUST-RUN。

### B3: Full-Proof Information Gain

- 检验 claim：C1。
- 为什么需要：这是最接近 InfoGain-RAG 原始叙事的 metric，应该和 action/patch 并列保留。
- 数据 / split / task：
  - 使用 B1 prefix manifest。
- 比较系统：
  - 同 B2。
- Target：
  - final verified proof text 或 final verified code region，取决于 trace schema。
- Metrics：
  - `IG_sum`；
  - `IG_avg`；
  - per-token logprob delta distribution；
  - length-normalized score；
  - 如果 full proof 超出 scorer context 或 target-token threshold，用 deterministic chunked score。
- 设置：
  - full proof 只能作为 scoring target；
  - artifact generation 和 context 都不能包含 final proof；
  - target 过长时记录 chunk boundaries。
- 成功标准：
  - full-proof IG 与 action/patch-span IG 方向一致，或其噪声能被清楚解释。
- 失败解释：
  - full-proof IG noisy/negative 不否定方法，只说明 long proof likelihood 不是稳定 metric。
- 表格目标：
  - 若稳定放主文，否则放 appendix。
- 优先级：MUST-RUN。

### B4: Patch-Span Information Gain

- 检验 claim：C1, C2。
- 为什么需要：patch-span IG 聚焦真实修复内容，不评分整个 final proof。
- 数据 / split / task：
  - 使用 B1 prefix manifest。
- 比较系统：
  - 同 B2。
- Target：
  - 从 `prefix_code` 到 `final_verified_code` 的 deterministic proof-relevant diff。
- Patch-span extraction algorithm：
  1. 计算 `prefix_code` 和 `final_verified_code` 的 textual diff。
  2. 保留包含 proof/spec markers 的 hunks，例如 `assert`, `proof`, `requires`, `ensures`, `invariant`, `decreases`, `lemma`, `by {`, `reveal`, `forall`, `exists`, `trigger`, `calc`, `assert_by`，以及 Verus ghost/proof constructs。
  3. 如果有 location metadata，优先保留与 selected verifier error 同 function 或 line neighborhood 的 hunks。
  4. 如果 retained hunks 超过 target-token budget，按与 selected error 的 proximity 取 deterministic top-K，并记录所有 dropped hunks。
  5. 如果没有 proof-relevant hunk，fallback 到 selected function 里最小 changed hunk，并标记 `patch_fallback=true`。
- Metrics：
  - `IG_sum`；
  - `IG_avg`；
  - hunk-level IG；
  - fallback ratio；
  - target length 和 dropped-hunk statistics。
- Reviewer audit requirement：
  - 每个 sample 保存 `prefix_code_hash`, `final_code_hash`, retained hunks, dropped hunks, marker matches, truncation reason；
  - metric pipeline 禁止人工编辑 hunk。
- 成功标准：
  - patch-span IG 比 full-proof IG 更清楚地区分 `trace_rationale` 和 `irrelevant_control`。
- 失败解释：
  - 如果 fallback 比例太高，patch-span metric 暂时不能作为主 claim。
- 表格目标：
  - 主文 Table 2 或 diagnostic Figure。
- 优先级：MUST-RUN。

### B5: Scorer Feasibility and Auditability

- 检验 claim：C1 前置条件和 anti-claim control。
- 为什么需要：我们需要 token-level evidence，而不只是 aggregate scores。
- 数据 / split / task：
  - 先 3-5 trace smoke test；
  - 再 20-50 trace probe。
- 比较系统：
  - local QwQ-32B HF/vLLM scorer；
  - optional cloud scorer：DeepSeek/OpenAI/Gemini logprobs。
- Metrics：
  - scorer success rate；
  - cost/time per target；
  - context overflow rate；
  - artifact ranking 在不同 scorer 间的一致性；
  - token-level records 是否完整。
- 设置：
  - 第一优先级：本地 QwQ-32B，如果能通过 HF/vLLM 做 teacher-forced token logprob；
  - cloud API 只作为 fallback/sensitivity，因为通常给 output-token logprobs，而不是 raw logits；
  - 如果 cloud API 不能 score arbitrary target text，就不能作为主 scorer。
- Required token-level output schema：

```text
sample_id
trace_id
prefix_id
target_type              # action | full_proof | patch_span
artifact_type            # none | generic_skill | trace_rationale | irrelevant_control
artifact_id
condition                # baseline | artifact_conditioned
token_index
token
token_bytes
prob
logprob
top_logprobs_json
target_region
chunk_id
scorer_model
scorer_backend
```

- Required aggregate output schema：

```text
sample_id
target_type
artifact_type
sum_logprob_baseline
sum_logprob_artifact
avg_logprob_baseline
avg_logprob_artifact
ig_sum
ig_avg
target_token_count
context_token_count
truncation_reason
scorer_model
```

- 成功标准：
  - 每个 aggregate score 都能追溯到 token-level records；
  - QwQ-32B local scoring 至少能跑通 3-5 trace smoke test。
- 失败解释：
  - 如果当前 QwQ-32B wrapper 不能 teacher-force target scoring，先换本地 scorer，不要急着依赖 cloud API。
- 表格目标：
  - appendix scorer audit table。
- 优先级：MUST-RUN。

## Run Order and Milestones

| Milestone | 目标 | Runs | Decision Gate | Cost | Risk |
|---|---|---|---|---|---|
| M0 | 检查 trace schema 并构建 prefix manifest | R001 | 能否把 3 条 verified hands-on traces 切成 stable states？ | low CPU | 不同模型 trace 字段不一致 |
| M1 | 构造 deterministic targets | R002-R004 | action/full-proof/patch target 是否非空且可审计？ | low CPU | patch extraction 太噪 |
| M2 | scorer smoke test | R005 | 本地 QwQ-32B 是否能返回 target token logprobs？ | 1 local GPU, small | QwQ wrapper 可能不支持 teacher forcing |
| M3 | 3-5 trace IG sanity | R006-R008 | trace rationale 是否优于 irrelevant control？ | small GPU | prompt artifact 主导结果 |
| M4 | 20-50 trace probe | R009-R011 | 结果是否稳定到值得继续方法迭代？ | moderate local GPU | full-proof context overflow |
| M5 | sensitivity/failure analysis | R012-R014 | 三类 metric 是一致还是可解释地分歧？ | optional | metric story 可能分裂 |

## Compute and Data Budget

- 预计 GPU-hours：
  - M0-M1：CPU only；
  - M2-M3：约 1-4 local GPU-hours，取决于 QwQ-32B 加载和 target length；
  - M4：约 10-40 local GPU-hours，full-proof scoring 最贵。
- 数据准备：
  - verified hands-on trace manifest；
  - repair state/action metadata parser；
  - deterministic diff/patch-span extractor；
  - artifact generator，输入 schema 中不能有 final proof。
- 人工审核：
  - 在 M4 前审核 10-20 个 patch-span extraction examples；
  - 审核 artifact generation prompt，确认没有 final-proof leakage。
- 最大瓶颈：
  - long proof/code target 的 teacher-forced token logprob scoring。

## Open Technical Decisions

1. QwQ-32B scorer 的具体路径和 backend：
   - preferred：local HF/vLLM path，能暴露 token logprob；
   - fallback：其他本地 teacher-forcing scorer；
   - cloud APIs 只在能 score arbitrary target 时进入主实验，否则仅 sensitivity。

2. peer-success action 的 state/error signature：
   - 只能用 train split；
   - 初步 key：project, error type, selected-error normalized text, function context, previous action/error motif。

3. patch target 最大长度：
   - 先 inspect target length distribution 再设 token budget；
   - 所有 truncation 必须记录原因。

4. artifact generator：
   - 可以使用 `state_t`, verifier error, prior history, generic skill library；
   - 不能使用 final proof、future trajectory states、held-out peer outcomes。

## Risks and Mitigations

- Risk: Full-proof IG 被长度和风格主导。
  - Mitigation: action IG 和 patch-span IG 并列报告，并保存 token-level diagnostics。

- Risk: Patch extraction 看起来 arbitrary。
  - Mitigation: deterministic diff、proof-marker filter、proximity rule、retained/dropped hunk audit。

- Risk: Action target 稀疏或歧义。
  - Mitigation: 先用 `primary_action`，再派生 coarse category 和 train-only peer-success target。

- Risk: QwQ-32B 当前 wrapper 无法 teacher-force logprobs。
  - Mitigation: 把 scorer feasibility 设为 M2 gate；失败就先换 scorer，不跑大实验。

- Risk: Artifact 泄漏未来 proof 信息。
  - Mitigation: generation 和 scoring 分离；artifact generation input schema 排除 final proof 和 future states。

- Risk: Metric 不预测 live improvement。
  - Mitigation: 这轮不 claim solved-rate improvement；只 claim metric validation / skill-promotion probe。
