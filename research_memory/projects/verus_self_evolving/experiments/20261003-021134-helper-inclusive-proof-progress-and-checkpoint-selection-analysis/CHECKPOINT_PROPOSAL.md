# Evidence-bounded three-checkpoint proposal

This is a recommendation for user review, not an activated selector or a claim
that a particular family has demonstrated hint benefit. Three filled checkpoints
per task is confirmed; do not reopen that requirement.

## Retain the user's intuition, repair its inputs

The start of a long platform is a useful preventive-hint hypothesis: hindsight
identifies a long upcoming episode. The problem was not that this idea is invalid,
but that target-only line overlap omitted helper work, counted textual rewrites
as regression, and sampled sparsely. Even with helper inclusion, only4 of38
primary tasks have3 pure platforms. Error reductions can still occur on a flat
combined curve. Long duration is therefore cost exposure, not intervention value.

## Proposed algorithm

1. Keep the fixed, pruned target/helper reference and component curves. Attach
   compile category, reported failed obligations, helper changes and action history.
   Separately retain relevant exploration outside the final dependency closure.
2. Build failure/search episodes. Group attempts to establish the same missing
   fact, even when moved between assertions/postconditions or tried via different
   APIs. Ignore filename/line shifts; do not merge solely on generic error category.
   Concrete identifier, obligation and premise evidence matters. This semantic
   grouping currently requires case review; literal stderr signatures are weaker.
3. Candidate families: (a) starts of long combined-progress plateaus; (b) starts
   of repeated unresolved-obligation/unsuccessful-attempt episodes; (c) before
   and after actual structural/API dead-ends, with separate preventive/diagnostic
   labels. Helper gains/error improvement annotate and downgrade a suspected
   stall rather than automatically excluding it. Textual drops alone are not
   sufficient regression evidence.
4. Tentatively prefer a well-identified recurring knowledge gap, then long
   unresolved platforms, then documented API/regression episodes. Within a family,
   sort by observed subsequent episode token exposure. This is an interpretable
   research prior, not an empirically fitted utility score. Prefer distinct
   episodes/knowledge gaps before taking both sides of one regression.
5. Fill to3 with safe presolution context boundaries: initial strategy state,
   completed relevant read context, or available failed-verifier diagnosis. Use
   `(event_index, code_hash, prefix/context identity)`, not code hash alone.
   Exclude known passing code, post-success states, target-absent probes and
   prefixes with future information. Validate original-task preservation and
   actor replay before actual forks. Availability alone does not imply usefulness.

Repeated-obligation starts and first precise wrong-API diagnoses are the stronger
current hypotheses because they expose a specific missing fact or invalid action
for a hint/card to address. Pure long-platform starts remain the required
comparison, particularly for long knowledge-search episodes. No offline observation
shows that these recommendations save more tokens than the user's heuristic.

## Value experiment needed later

Use identical historical prefixes and matched hint/no-hint continuations for
each candidate family, including the original long-platform-start comparator.
Assess full Verus+preservation success and remaining suffix tokens/time, accounting
for hint cost, failures, repeated runs and duplicated prefixes. Do not optimize
the selector on sealed test tasks. Native SkillOpt fast-update cards and later
600s downstream evaluation remain separate; neither is launched by this audit.
The1800s training collection and expense-record-only policy are unchanged.
