# Router prompt review: understandable, but v1 underspecified

## 结论

如果给我v1和完整输入，我能知道要做的是“离线组织卡库，输出类别和归属JSON”，
不是求解一道Verus题。但我不能从v1唯一确定有用的分类粒度，也不能保证另一模型
不会按主题词泛分或把多用途卡的适用条件压成一条。先前把它称为可审阅草稿是
合适的，不能因此称为已验证适用于Verus的router。

本次按实际repaired78中15张卡（006/018/023/045/047/052/055/057/058/062/
065/068/069/071/074）的正文检查边界并修订v2。没有运行DeepSeek、没有全库分类，
没有执行Verus验证；以下是源文本层面的审查，不是模型分类准确率或性能结果。

## v1的主要缺口与v2修正

| 缺口 | 可能的错误 | v2修正 |
|---|---|---|
| 最终读者和用途不具体 | 输出验证领域知识分类，而非可选读目录 | 说明actor只能看当前goal/code/diagnostic，交付是目录而非解题 |
| 分类粒度不明确 | 过粗“quantifiers”，或每张卡一个类别 | 给出过宽/过窄判据，以可辨认的修复决策区域为单位 |
| 只有每卡一个特征元组 | 018/057的多诊断条件被压成一个 | card内显式cases；整卡唯一存放，case可带条件跨链接 |
| Verus只是角色名称和少量例子 | 混淆证明失败、scope/type、Lynette差异、成功后清警告 | 明确入口状态及Verus/temporal/ghost边界检查，不强制固定分类表 |
| 缺少源文定位和内在矛盾处理 | 模型凭“常识”扩展适用性，或自动修正卡内容 | 每case源文短摘录；跨字段冲突必须review，不静默补知识 |

“可辨认的修复决策区域”并不要求唯一正确taxonomy。同一组可以保留多个条件分支；
细分或合组是否合理，要看当前状态能否选对、条件是否保留，而非类别数量是否漂亮。

## 源卡边界检查：期望行为，不是硬编码分组答案

| 实际卡 | 正文支持的情形 | Router应保留什么 |
|---|---|---|
| 006、023、069、074 | 量词证明体中的前提不可用；023还有binder遮蔽问题 | 以前提/scope诊断为入口，不泛化为所有量词错误；保留不同动作/版本约束 |
| 018、057 | missing antecedent与trigger inference两个独立诊断 | 至少区分两个case；可以一个有明确分支的family，也可条件化跨链接 |
| 058 | 已有entailment/validity假设，具体执行上的项形状未激活实例化 | 不能与“缺少前提”当同一诊断，也不等于自动trigger推断报错 |
| 052 | 证明已通过，仅清trigger/implication警告 | entry为verified warning cleanup，不能作为未通过证明的修复入口 |
| 045、047、062、071 | 利用已有规则证明always合取的稳定性 | 保留目标形状、helper可用性、lifting/always层次和结合顺序；不是所有temporal题 |
| 055、065、068 | scope/import与proof-only保持相关；另有条件化后续动作 | 名称解析/保持边界与逻辑证明边界分开；068的序列等式义务不能丢 |

值得显式审查的细节：018的Action说两种诊断分开处理、互不必然需要；Validate
却把改implication和加trigger一起叙述。模型可能误读为必须同时做两步。
应标记这处措辞张力供审查，不能在router阶段悄悄改正文，也不能把它当两步都必要
的证据。此处不是重新运行后的逻辑错误判定。

## 给我修订后的prompt，我会怎样执行

1. 读完整卡库，确定各卡是在什么可观察状态下适用，不先指定“量词/时序”等目录。
2. 提取带原文定位的cases；同卡不同诊断分开记录，正文不拆改。
3. 比较全部cases，提出能区分相邻问题的family和入口/排除条件。
4. 为整卡选一个存放位置，为其他cases补带条件链接；不复制正文或重复计支持。
5. 输出JSON候选、重复/互补/冲突关系和需要审查的问题；不假装已经reduce或部署。

只有system prompt仍不能实际分类，必须同时传入README约定的完整JSON卡包。
只有原始cards.json也不等于消息已经构建好：ID列表、哈希和修订短描述需要由程序
装配并校验。程序验证器/renderer尚未实现；prompt中写了约束不代表约束已经执行。

## 下一步如何验证，而不是继续堆prompt

- 先实现结构检查：78/78、case覆盖、原文摘录匹配、路由互不矛盾、链接可解析。
  其中语义不矛盾仍需人工/独立审查，JSON检查本身不能证明。
- 经授权后做一次全库构建，检查是否遵循上述真实卡边界；这些卡来自训练提炼库，
  不读取validation/test结果来修改类别。保留原始输出和修订记录。
- 不能只抽查“看起来合理”的组：检查全部归属以及所有冲突、跨链接和近重复关系。
- 冻结一个候选后才评测同轮A/B；目录可理解不等于已经提高检索或解题表现。
