# new_prose: ten card bodies

Exact card content from the evaluated bundle. The actor reads these on demand.

## new-001

**Trigger:** The current failed obligation is a finiteness postcondition for the set produced by recursively accumulating over a finite input set, and the proof body is empty or has just introduced an unverified recursive proof routine; the remaining goal is to connect the accumulator's branch behavior to finiteness without assuming a missing premise.

**Action:** Inspect the current postcondition diagnostic, the declarations of the recursive accumulator and target proof obligation in scope, and the branch structure already present in the proof body. Within the current proof scope, bind the finite input set and its explicit finiteness premise. In a nonempty branch, also bind the result of removing an element and the accumulated result on that reduced input; keep the empty branch separate. Compare the active branch's accumulated result with the insertion relation on the reduced result and with the empty-set base relation, checking only whether those relations are already available from the definitions in scope. If the active branch result is known to be an insertion into a reduced result whose finiteness has been proved, check preservation of finiteness through that insertion and its connection to the target result. In the empty branch, check the empty-result relation and finiteness from the available definitions. Leave any missing relation as an obligation, not an assumed equality. If the insertion preservation or empty base finiteness is not discharged, do not add further equality assertions; instead inspect whether the reduced input is provably finite and strictly smaller before considering any recursive call.

**Why:** Reviewed windows show edits that added a recursive proof routine and a call from the target before passing Verus runs, but each edit was bundled with no admitted intermediate check; the necessity of the routine split, equality form, or particular branch condition is therefore not established.

**Validate:** Re-run the same finiteness postcondition after the branch-level probe; if the postcondition is now established, record which branch relation was used, and if it remains unsatisfied, check whether a missing smaller-input finiteness premise is the remaining blocker rather than the final finiteness transfer.

**Avoid when:** Stop this route if the finite-input premise cannot be justified. In a recursive branch, stop if neither a supported finite reduced result nor a justified smaller-input recursive step is available. These recursive conditions do not apply to the empty branch; do not assume a missing branch relation.

## new-002

**Trigger:** The current obstruction is a failed callee precondition or local assertion inside a loop over a packet collection. A required per-element property may be available outside the loop but absent or unapplied at the current call site; diagnose this from the current source rather than requiring the historical sequence of failed attempts.

**Action:** Inspect the failing precondition or assertion diagnostic and the immediately preceding loop invariants and local proof statements. Determine which per-packet and source-endpoint facts are currently available at the call site. Bind the current packet collection, its view length, the current index, the client endpoint before the loop, and the client state inside the loop. Also bind the current loop invariant set and any proof helpers that are in legal scope at the same index. Compare the per-packet validity fact and source-endpoint equality required by the callee precondition with what the loop invariants currently state about that same index. Do not conclude they match merely because a sequence-level property is present somewhere else. If a required sequence property is missing from the loop invariants, check whether current entry facts establish it and every iteration preserves it before proposing that property as an invariant; verify both obligations. If the property is already present but unapplied at the current index, inspect an available instantiation rule and its actual preconditions, then try one justified application. Do not invent a helper or assume either obligation. If the same precondition still fails, inspect whether the invariant or helper references the same view and index, whether the endpoint is expressed before or inside the loop, and whether a different unsupported fact is now exposed. Do not assume the missing premise is true without proof support.

**Why:** Reviewed attempts show that sequence-level assertions placed before and inside the loop, and added but uninvoked proof helpers, did not clear the loop-body assertion or precondition failures. This does not establish whether the missing support is quantifier instantiation, precondition visibility, a missing loop invariant, or a combination of these.

**Validate:** Run the same verifier command and inspect whether the same callee precondition or assertion is still reported. If the failure moves to a new location, classify the new obligation separately before making another edit.

**Avoid when:** Stop when the required property or index bound cannot be derived in the relevant scope or proved as an invariant, when no applicable instantiation rule is available, or when the probe would assume a premise or change executable behavior. A fact absent from the existing invariant list is a diagnostic condition, not by itself a reason to abandon checking whether it can be established.

## new-003

**Trigger:** The current Verus diagnostic reports a precondition failure at a call to the forward-preservation helper. The unfilled requirement is the universal step relation saying that whenever the invariant and the next predicate hold at a suffix, the invariant holds at the immediate suffix.

**Action:** Inspect the stability and witness proof body at the forward helper call, the called helper's quantified step requirement, and the universal always-fact that has already been propagated to the chosen base execution. Note any local aliases that rename the base execution or the implication predicate. Bind the base execution, its relation to the current starting index, an arbitrary step index, and the predicates named by the actual helper contract. Determine from that contract which execution argument each premise concerns; keep shifted facts within that scope instead of presupposing that the original execution and base execution are interchangeable. Compare the step relation at an arbitrary suffix of the base execution with the form required by the helper's quantified step requirement. Also compare any local alias expression with the expanded suffix and predicate form used when the universal always-fact was established. Before calling the forward helper, prove the universal step relation at an arbitrary suffix in the exact base-execution form the helper requires; if that succeeds, call the helper. The remaining obligation is the step relation for an arbitrary suffix, not the helper's final conclusion. If the probe fails, hold the current suffix and inspect which side of the step relation is unjustified. If no expression mismatch appears but the step relation still fails, check whether the corresponding universal always-fact is available at the base execution and at the shifted index. If neither is available and no existing rule can derive it from the current premises, stop rather than assume the quantified step or modify the helper's prerequisite.

**Why:** Reviewed training windows show the same forward helper precondition failed after the field-call syntax repair. Later attempts explicitly proved the quantified step relation before that call, and the indexed checks then reported seven verified with no errors; one passing branch retained local aliases, and another later change altered the way the step assertion was expressed, so neither inlining nor a single assertion form is established as necessary.

**Validate:** Re-run the same Verus command and inspect the same quantified helper precondition and the added local step proof. Confirm their verification before treating the step fact as available; a diagnostic merely moving elsewhere is not independent evidence that each earlier assertion passed. Treat another unresolved conclusion as a separate obligation.

**Avoid when:** Stop when the helper call is absent, the quantified step is not among the current premises or derivable from the supplied rules, the failure is not the helper precondition, or the only route would assume the missing step or alter the original contract.

## new-004

**Trigger:** The current failed obligation is a set-extensionality assertion: a membership equivalence between the image of a union and the union of two images. The failure is an assertion failure rather than a parse or name-resolution error, and the active proof block already binds the two domain sets and the mapping function.

**Action:** Inspect the failing membership-equivalence assertion and the surrounding quantified proof block, including which conditional branch is active and which membership or image-equality premises are already in scope for the current range element. Bind the current range element, the two domain sets, the mapping function, and the active branch of the quantified proof block. Compare membership of the current range element in the image of the union with its membership in the union of the two images, and identify which direction the active branch must still establish. If the active branch assumes membership in one of the two images, check whether the in-scope premises already provide a source element with that membership and an image equal to the current range element. If such a source element is in scope, use it to derive the required union containment; if no such premise is in scope, do not introduce a missing premise. If a source element is not yet bound, inspect whether the active image-membership premise and accessible definitions justify its existence. If they do, check the installed witness-selection construct and its contract before binding such an element and proving the required membership and image relation. Otherwise leave the witness connection unresolved; do not merely repeat the containment assertion or switch to an unspecified repair.

**Why:** In this training group, after the parse structure was corrected, the quantified membership-equivalence assertion still failed, and an earlier branch that only asserted the negative union membership also failed. A later nearby transition changed the source-element extraction form and a subsequent run reported success, but only a single nearby edit separates those checks and the exact mechanism was not isolated, so witness reasoning remains an uncertain hypothesis rather than a known necessity.

**Validate:** Re-run the same failed assertion or enclosing postcondition and inspect whether the original membership-equivalence obligation closes or the same line still fails. Treat a new or shifted failure as a signal to inspect the active branch premises rather than assume the source-element relation is sufficient.

**Avoid when:** Stop if neither an existing source-element premise nor a justified existence argument supports the required image relation, if the selection construct cannot be applied legally, or if the probe would introduce an assumption. A missing already-bound witness alone does not rule out deriving one from image membership; historical success establishes no universal witness necessity.

## new-005

**Trigger:** A final entailment obligation remains open even though pointwise and temporal-lifting reasoning is present. Determine whether that reasoning is actually proved or only attempted, and whether the given temporal hypothesis has been instantiated for the execution at the open obligation.

**Action:** Inspect the open entailment, the declaration of entailment and its underlying quantified premise, and the available temporal predicates. Read the actual contract or definition that can connect the source and destination predicates. Bind the arbitrary execution required by the current obligation. Within a justified source-satisfaction branch, bind the source and destination predicates according to the current contract. Keep consequences within this execution and premise scope. Compare the complete quantified conclusion supplied by the hypothesis, instantiated at that execution, with the local expression being used. Check which premise must be established before the consequence is available; use the actual source-to-destination direction instead of a generic/specialized name-based guess. Only if the declaration and current premises justify it, expose the full instantiated hypothesis at the bound execution and verify that local assertion before deriving its consequence. Discover its expression from the current declaration; do not substitute into a historical successful formula. The destination property remains to be proved, never assumed. If the instance is justified but the final entailment is still open, check the actual pointwise implication and temporal-lifting obligations in the direction required by the current goal. If a link is unavailable, leave it unresolved and inspect its supporting premises rather than reversing it or borrowing an unproved relation.

**Why:** Reviewed endpoints include a failed direct entailment assertion and failed generic transitivity reasoning. A later passing state added full premise instances, removed the helper and changed the outer assertion together; the suffix reasoning was already present. This supports a conditional inspection of premise instances, not isolated causality, an observed SMT firing or a universally sufficient expression.

**Validate:** Re-run the verifier on the same final entailment postcondition. If it passes, stop; if an intermediate assertion fails, use its location to decide whether the missing link is hypothesis instantiation or the pointwise strengthening, and do not repeat the same edit without a changed diagnostic.

**Avoid when:** Stop this route if no source-satisfaction scope is justified, the hypothesis cannot be instantiated at the required execution, or the actual pointwise/temporal connection cannot be derived. Do not assume obligations, reverse an implication, or weaken the specification.

## new-006

**Trigger:** An empty or incomplete proof body leaves a temporal stability postcondition open for a conjunction of temporal predicates constructed from state predicates. Inspect the exact temporal wrappers: local stability and conjunction rules may be used only when their real input shapes and premises match the goal.

**Action:** Inspect the failed proof function declaration, its empty body, the exact postcondition being failed, and the local temporal proof rules that establish stability of an always-lifted predicate and stability closure under conjunction. Bind the current proof function parameters, the exact failing postcondition, the empty body, and the available stability and conjunction rules in the same module scope. Treat the postcondition as unproved and assume no missing premise. Compare the outer temporal structure of the failing postcondition with the conclusions of the available local rules. Determine whether the whole claim is a validity/stability claim over a conjunction, and whether each conjunct is an instance of the individual stability rule's input shape. If the comparison shows the local stability and conjunction rules can license the current postcondition, add a proof-only derivation using the available local composition machinery in the order dictated by the postcondition's structure, preserving all specifications and termination measures. Then run Verus and read the complete diagnostics. If composition fails, inspect its actual rule or macro expansion before decomposing it. Only if the inspected contracts justify the decomposition, prove the required stability fact for each operand in its valid scope and then discharge every premise of the conjunction rule. A proof for one operand does not justify the remaining operands; otherwise leave the unsupported connection open.

**Why:** Reviewed evidence shows one adjacent source edit that replaced an empty proof body with a proof-only invocation of local composition machinery over four lifted state predicates. Before the edit, Verus reported the postcondition unsatisfied with zero verified and one error; after the edit, it reported one verified and zero errors. The observation is aggregate and correlational: it does not isolate which helper-internal obligation, conjunct count, or ordering property was necessary, and no counterfactual body or alternative ordering was reviewed.

**Validate:** Re-run the same Verus obligation on the current candidate and read the full diagnostics. Interpret an aggregate one-verified, zero-errors result only as closure of the whole postcondition for this file, not as proof that each local proof step was independently discharged. If the same failure repeats, inspect the first new diagnostic and change strategy rather than repeating the same edit.

**Avoid when:** Stop when the proof function no longer has the empty-body postcondition and the same obligation is discharged by Verus, or when a missing or incompatible premise or rule type prevents lawful application. Do not continue merely to remove pre-existing warnings or change executable and specification code.

## new-007

**Trigger:** The current failed diagnostic is a reveal rejection on the closed little-endian conversion function, or a serialized-length assertion that cannot see the closed function body. This operation applies when the closed-function diagnostic or an equivalent serialized-length obligation remains the immediate failed verification goal and the bytes module is available for inspection.

**Action:** Inspect the bytes module declarations for the closed conversion, any open conversion with the same intended meaning, and any proof whose postcondition explicitly relates the closed form to the open form. Also inspect the available sequence-length facts for the open definition. Bind the current 64-bit value whose serialization length must be established, the closed serialization term, the open serialization term, and the scope in which the serialization trait body is visible. Do not bind the closed function body because the diagnostic states it is not visible. Compare the structure and length consequences of the open conversion definition with the closed conversion term. Compare any connector proof's stated consequence against the equality needed to transfer a length fact from the open form to the closed form. If a connector proof with the stated closed-equals-open consequence is present, invoke that connector and then assert only that the open serialization term has the expected length. Use the rerun diagnostic to determine whether the open length fact is discharged before attempting to transfer it to the closed form. If no connector consequence is available or the open length is not discharged, do not attempt to reveal the closed function again. Determine whether a general byte-width fact in the bytes module can be instantiated at the current value, and only then attempt to connect that fact to the closed serialization term.

**Why:** One reviewed window showed that the closed little-endian conversion function rejected a reveal diagnostic, and a separate later transition removed that path in favor of an open form and connector version but immediately produced a syntax error at an ensures. This supports inspecting the allowed open and connector relationships, not copying that later formula.

**Validate:** Re-run the verifier after any permitted connector call or open-length assertion, and check the original serialized-length obligation. Determine whether the original closed-term length assertion is now discharged or whether the transfer step remains the failing goal.

**Avoid when:** Stop if the bytes module provides neither an open definition nor an explicit consequence relating the closed and open forms, or if the open length cannot be established without an unadmitted premise.

## new-008

**Trigger:** The current Verus diagnostic reports a postcondition failure at the end of an empty proof body for the target equality, and the existing temporal predicate definitions and helper proof functions are available unchanged.

**Action:** Inspect the current failed postcondition and the precondition of each available helper proof function to identify which helper requires a pointwise pair of entailment premises. Bind the current predicate values and the two pointwise predicate-family arguments required by the inspected helper contract. For its local entailment checks, bind an arbitrary element of the required family type within the appropriate proof scope; do not reuse historical argument names or presume the two families are equal. Compare each required entailment direction between the two bound pointwise predicates with the definitional form of entailment at that same arbitrary element, without assuming either direction holds. If the helper precondition is the current unresolved subgoal, add proof-block assertions for each entailment direction separately and rerun Verus before invoking the helper; do not invoke the helper until both assertions are accepted. If no precondition mismatch is identified or the probe reports a failure on either direction, inspect the unfolded definitions of entailment, validity, implication, and always for that element rather than assuming reflexivity or proceeding to the equality chain.

**Why:** Reviewed evidence bundles a single source transition that adds two pointwise predicate families, a mutual entailment assertion, and two helper calls, with aggregate Verus moving from 0 verified, 1 error to 1 verified, 0 errors. This collectively associates the additions with closure but does not isolate any component; per-assertion and safety-comparison results are not present in the indexed window.

**Validate:** Re-run Verus on the same target postcondition. Interpret a changed diagnostic as separation of the new precondition obligation; only accept if the original postcondition is reported verified, and do not infer helper contribution from a shell exit status alone.

**Avoid when:** Stop this route if the candidate helper does not require the relevant pointwise entailment premises, its types or conditions do not match the current equality obligation, or either direction cannot be justified. Do not reuse the historical lambda names or equality chain as a fixed template; the empty-body observation is evidence context, not a requirement to match the historical source verbatim.

## new-009

**Trigger:** The verifier currently reports that a quantifier in the pointwise execution equality proof has no inferred trigger, after field-projection syntax has already been corrected enough to reach trigger inference. What remains to be proved is the pointwise equality over an arbitrary index that is needed as a precondition for the execution equality lemma, without assuming any missing premise.

**Action:** Inspect the immediate trigger diagnostic and the quantified equality assertion at the reported source span. Identify the bound index, the two compared spec-function applications, and any trigger annotations already present in that quantifier body. Bind the current execution arguments and the arbitrary index variable from the quantifier scope. Do not bind a concrete witness or suffix arithmetic expression, and do not absorb later proof obligations. Compare the existing trigger annotations in the quantifier body, if any, with the diagnostic claim that no trigger could be inferred. Compare the syntactic shape of the two compared function applications and which legal call or projection terms occur in the body. If no legal existing term in that quantifier body is annotated, select one existing function-call or field-projection term from the body and add a single trigger annotation to it, without copying a historical side choice and without annotating more than one term at once. Rerun the same verifier command. If the missing-trigger diagnostic persists after one legal annotation, inspect the reported trigger shape and choose a different existing call or projection term. If no legal term remains, stop this action and report that the current equality formulation needs restructuring before the proof can proceed.

**Why:** Reviewed evidence shows that after field-projection syntax was corrected, a missing-trigger diagnostic appeared on the pointwise equality quantifier, and later checks with trigger annotation on at least one existing term passed. No minimal trigger placement is established because the available fork shares the earlier prefix, so the evidence supports bounded inspection, not a universal side or sufficiency claim.

**Validate:** Rerun the same verifier command on the same pointwise equality obligation and read the next diagnostic. If the missing-trigger diagnostic disappears and the enclosing proof reaches its next obligation, treat only that local trigger failure as addressed; if a later proof failure appears at another location, classify it as a separate decision rather than evidence that the annotation is sufficient elsewhere.

**Avoid when:** Stop if no legal function-call or field-projection term remains available as a trigger in the current quantifier, if the diagnostic says the current terms cannot be used as triggers, or if further annotations would require changing the specification or the asserted proposition. Also stop this action when the same obligation passes and open a separate action for any subsequent failed obligation.

## new-010

**Trigger:** A proof assertion inside a universally quantified entailment fails verification, and the diagnostic indicates that an outer implication does not make its antecedent available in the body; the inner obligation depends on that antecedent.

**Action:** Inspect the failing assertion body and the exact inner obligation requiring a current execution or suffix as a premise, along with the formula enclosing the universal quantifier. Bind the arbitrary quantified values already introduced by the universal assertion and any current execution or index required by the inner obligation without adding new variables beyond what the proof scope requires. Compare the premise the inner proof needs with the assumption actually available under the current outer formula; determine whether the antecedent is in scope as a hypothesis or only as part of a compound expression. If the needed antecedent is not available in the proof body, inspect the implication assertion form accepted by the current toolchain and the current proposition. Introduce a justified conditional branch on that antecedent where the proposition requires its consequent, keeping the complementary case and outer implication as proof obligations. Retain any existing local proof steps inside their valid scopes; do not require a particular disjunction formula or an equality-lemma chain. If the assertion still fails, inspect the actual remaining premise, index or object relation identified by the diagnostic. If existing equality reasoning is relevant, verify that it concerns those same objects; otherwise leave that route unused. Do not repeat the same formulation or introduce an unsupported relation.

**Why:** Neighboring evidence shows a source state using an outer implication with explicit antecedent branches produced a passing Verus check, while another state rewriting to a disjunction also passed without visible implication warnings. The check alone does not isolate the branch from retained equality proof steps, and warning absence is based on visible stdout only.

**Validate:** Re-run the same Verus check on the same failed assertion and confirm whether the inner assertion is now discharged; if warnings remain, record whether they are fatal or nonfatal.

**Avoid when:** Stop if the antecedent cannot be made available without assuming or admitting it, or if the obligation is not discharged after explicit branching and supported equality connections; do not infer that a passing check validates a missing premise.
